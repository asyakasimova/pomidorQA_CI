# Покрытие требований PomidorQA

Дата оценки: 20 сентября 2026 года. Источник: [requirements.md](requirements.md). Оценена текущая рабочая копия, включая незакоммиченные тесты.

## Методика

Это статическая оценка проверок в коде, не процент успешных прогонов и не покрытие строк приложения. В рамках этого аудита выполнен сбор тестов (`npx playwright test --list --reporter=list`), полный прогон не запускался.

Единица учёта — явно сформулированное проверяемое условие. Повторы из разделов 2, 3 и негативных критериев раздела 13 объединены с основными правилами. Сквозной положительный путь раздела 13 оставлен отдельным интеграционным условием: отдельные тесты шагов не доказывают весь путь. Назначение продукта, функции вне MVP и сведения о готовых аккаунтах не входят в знаменатель. Условия обычной регистрации из раздела 14 включены в строку регистрации; перечень поясов — в профиль. Не добавлены отсутствующие в спецификации требования о пересечении слотов, уникальности email и бронировании несуществующего ID.

Это одна явно зафиксированная декомпозиция требований, а не единственно возможное число. Сохранены все 63 ID и формулировки предыдущей оценки. По запросу пользователя изменено только правило учёта HTTP-моков: теперь они засчитываются наравне с приложением. Это договорённость расчёта, а не подтверждение эквивалентности мока внешнему backend.

- **Полное** — есть явные проверки результата в реальном приложении или HTTP-моке для всей формулировки строки. Это не доказательство отсутствия всех возможных багов. Для пользовательских состояний free/booked достаточно соответствующего статуса или доступности в UI; технические статусы confirmed/cancelled не считаются доказанными одним попаданием в раздел.
- **Частичное** — проверена лишь часть вариантов, косвенный результат либо только интерфейсный запрет без фактической попытки обхода ограничения.
- **Нет** — нет подходящих проверок ни приложения, ни HTTP-мока. Учебные unit-функции сами по себе по-прежнему не засчитываются как проверки приложения: запрос на пересчёт касается моков.
- Один тест может подтверждать несколько строк; три браузера не утраивают покрытие. Полное покрытие считается без весов. Частичные строки не получают условных полбалла.

## Ограничения существующих проверок

- `booking-flow.spec.ts` с «гонкой» в названии сначала ждёт успеха первого участника, затем подтверждает вторым. Это последовательный конфликт, а не проверка одновременных запросов.
- `booking-api.spec.ts` запускает `startServer()` из `src/pyramid/mock-booking-api.ts`. Его 201/409 и статусы засчитываются в этой матрице наравне с приложением, хотя фактически проверяют реализацию мока.
- `src/pyramid/slots.ts` содержит учебные функции; их подключение к внешнему приложению не подтверждено.
- Запрет вчерашней даты проверяет `validity.rangeUnderflow`, запрет удаления booked — отсутствие кнопки. Это полезные UI-проверки, но серверные ограничения требуют отдельных запросов.
- Новый тест дубликата проверяет can_help после повторного POST и reload. Общий запрет для двух типов остаётся частичным до проверки want_to_learn.
- Тест ошибки входа сравнивает два текста, но равенство само по себе не исключает одинаковое раскрытие причины в обоих сообщениях.

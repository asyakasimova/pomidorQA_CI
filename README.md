# PomidorQA CI — автотесты на Playwright и TypeScript

Учебный проект автотестов для [PomidorQA](https://aiqa.su/pomidorqa) — сервиса встреч для QA/IT-специалистов. Репозиторий создан на основе материалов [курса](https://aiqa.su/base/aqa) и [исходного проекта](https://github.com/lebed52/pomidorqa-course-tests).

В проекте реализованы unit-, API- и E2E-тесты, проверки GitHub Actions и уведомления об успешном CI в Telegram. Исходного кода сайта здесь нет: E2E обращаются к готовому стенду, а для unit- и API-тестов используется вспомогательный код из `src/pyramid`.

## Требования

- Git.
- Node.js 24 и npm — эта версия Node.js используется в CI.
- Интернет для установки зависимостей и E2E-прогонов.
- Браузеры Playwright: Chromium, Firefox и WebKit.

Проверка окружения:

```bash
git --version
node --version
npm --version
```

## Установка

Для новой локальной копии:

```bash
git clone https://github.com/asyakasimova/pomidorQA_CI.git
cd pomidorQA_CI
npm ci
npx playwright install chromium firefox webkit
```

Если проект уже клонирован, открой терминал в его корневой папке и выполни только две последние команды. Корень проекта — папка с `package.json` и `playwright.config.ts`.

На Linux установи также системные зависимости браузеров:

```bash
npx playwright install --with-deps chromium firefox webkit
```

`npm ci` устанавливает зависимости из `package-lock.json`; файл должен соответствовать `package.json`. При намеренном изменении зависимостей используй `npm install` и сохраняй изменения обоих файлов в Git. Папки `node_modules`, `playwright-report` и `test-results` исключены через `.gitignore`.

## Настройка стенда

По умолчанию E2E используют `https://aiqa.su`. Для другого совместимого стенда передай `POMIDORQA_BASE_URL`:

```bash
POMIDORQA_BASE_URL=https://aiqa.su npm run test:e2e
```

Пример выше и команды с `CI=true` ниже рассчитаны на Bash/Zsh (macOS/Linux). В PowerShell переменная задаётся отдельно:

```powershell
$env:POMIDORQA_BASE_URL = "https://aiqa.su"
npm run test:e2e
```

Указывай адрес без `/pomidorqa`: пути тестов уже содержат этот префикс. Локальный `.env` автоматически не загружается текущим конфигом.

E2E создают тестовых пользователей через API, работают с профилями, слотами и бронированиями. В тестах предусмотрено удаление созданных пользователей. Готовые логины и пароли для запуска не требуются. Доступность внешнего стенда влияет на результат E2E. Если указать `localhost`, приложение нужно запустить отдельно: этот репозиторий не поднимает сам сайт.

Unit-тесты не требуют браузера и сети. API-тесты сами запускают и останавливают локальный HTTP-мок-сервер; внешний стенд им не нужен.

## Запуск тестов

Все команды выполняются из корня проекта.

| Команда | Назначение |
| --- | --- |
| `npm run lint` | Проверка кода в `tests` через ESLint |
| `npm run test:unit` | Unit-тесты |
| `npm run test:api` | API-тесты локального мок-сервера |
| `npm run test:e2e` | E2E во всех трёх браузерах |
| `npm test` | Все проекты Playwright |
| `npm run report` | Открытие HTML-отчёта последнего прогона |
| `npx playwright test --list` | Список тестов без выполнения |

Отдельный браузер:

```bash
npx playwright test --project=e2e
npx playwright test --project=e2e-firefox
npx playwright test --project=e2e-webkit
```

`e2e` — Chromium, `e2e-firefox` — Firefox, `e2e-webkit` — WebKit с профилем Desktop Safari. WebKit проверяет движок Safari, но не является установленным приложением Safari.

Один файл в Chromium:

```bash
npx playwright test tests/e2e/profile-flow.spec.ts --project=e2e
```

Запуск с видимым браузером или в режиме отладки:

```bash
npx playwright test --project=e2e --headed
npx playwright test tests/e2e/profile-flow.spec.ts --project=e2e --debug
```

Проверка с настройками CI:

```bash
npm run lint
CI=true npm test
```

При `CI=true` включены один worker, один повтор упавшего теста и запрет `test.only`; HTML-отчёт автоматически не открывается. Локально повторов нет. Общий таймаут теста — 30 секунд; сценарий выбора конкретного слота задаёт 60 секунд.

## Что покрыто тестами

|---|---:|---:|
| Полное | 24 | 38,1% |
| Частичное | 24 | 38,1% |
| Нет | 15 | 23,8% |
| **Всего** | **63** | **100%** |

Полное + частичное покрытие - 76,2%

Текущий набор содержит **40 сценариев**: 10 unit, 8 API и 22 E2E. 

### Unit: 10 сценариев

Файл: `tests/unit/slots.spec.ts`.

- Пересечение временных слотов: частичное пересечение, соседние границы, разнесённые интервалы в обоих порядках, вложенность и полное совпадение — 6 проверок.
- Отображение одного момента в разных часовых поясах и формат `HH:mm` — 2 проверки.
- Минимальная длина пароля: 7 символов не проходят, 8 проходят — 2 проверки.

Проверяются функции из `src/pyramid/slots.ts`.

### API: 8 сценариев

Файл: `tests/api/booking-api.spec.ts`.

- Бронирование свободного слота: HTTP 201, статус `confirmed`, корректные участники.
- Запрет бронирования собственного слота.
- Запрет бронирования слота в прошлом.
- Ошибка при бронировании несуществующего слота.
- Ошибка при повторном бронировании занятого слота.
- Два одновременных запроса на один слот: одна успешная бронь и один отказ.
- Регистрация участника с проверкой возвращаемых данных.
- Отказ при повторной регистрации с тем же email.

Эти тесты проверяют **локальный мок из `src/pyramid/mock-booking-api.ts`**, а не реальный backend PomidorQA.

### E2E: 12 сценариев в каждом браузере

| Файл | Сценарии |
| --- | --- |
| `tests/e2e/profile-flow.spec.ts` | 8: сохранение имени, часового пояса, Telegram и «О себе» с проверкой после перезагрузки; добавление навыка; запрет пустого навыка; навык «хочу разобрать» не попадает в «могу помочь»; одновременное сохранение трёх полей |
| `tests/e2e/booking-flow.spec.ts` | 2: создание слота, поиск хоста по навыку, бронирование и отображение встречи у обоих участников с отказом второму гостю; выбор второго из трёх времён с проверкой конкретного времени встречи и доступности остальных слотов |
| `tests/e2e/booking-cancel.spec.ts` | 1: отмена гостем бронирования, отсутствие предстоящей встречи у гостя и появление карточки в прошедших у гостя и хоста |
| `tests/e2e/login-error.spec.ts` | 1: одинаковая ошибка при неверном пароле и несуществующем email |

В E2E с двумя гостями оба заранее открывают подтверждение, после чего подтверждают бронь по очереди. Одновременные HTTP-запросы отдельно проверяются на API-уровне.

Для браузерных сценариев используются Page Object-классы `BookingPage` и `ProfilePage`, а также общие helpers создания и удаления пользователей. Покрытие не включает все функции продукта; успешный прогон подтверждает только реализованные проверки.

## Отчёты и диагностика

Playwright выводит результаты в консоль и создаёт HTML-отчёт в `playwright-report/`:

```bash
npm run report
```

Для E2E-проектов настроены скриншоты при падении, сохранение trace и видео при падении. Их наличие зависит от использованного браузерного контекста: часть тестов создаёт контексты вручную через `browser.newContext`, и параметры записи из конфигурации не подключаются к ним автоматически. Поэтому наличие всех вложений для каждого падения не гарантируется.

Если тест упал, проверь сообщение assertion, ожидаемый и фактический результат, доступность стенда и имеющиеся вложения. Если упал линтер, исправь указанный файл и правило до повторного запуска тестов.

## GitHub Actions

Workflow: `.github/workflows/playwright.yml`, имя в GitHub — **Playwright CI**.

Запуски настроены на:

- создание и обновление Pull Request в `main`;
- push в `main`, включая результат merge;
- ручной запуск через **Actions → Playwright CI → Run workflow**.

Обычный push в рабочую ветку без открытого PR не запускает этот workflow.

### Настройка репозитория

1. В GitHub открой **Settings → Secrets and variables → Actions → Variables**.
2. Создай repository variable `POMIDORQA_BASE_URL` со значением `https://aiqa.su` либо адресом совместимого стенда без `/pomidorqa`.
3. Убедись, что Actions разрешены и основной веткой репозитория является `main`.
4. Отправь файлы проекта и `package-lock.json` в репозиторий. Для ручного запуска workflow должен быть в основной ветке.

Переменную в GitHub нужно задать явно: workflow передаёт её в окружение тестов, а пустая строка не активирует резервный адрес, заданный через `??` в конфиге.

### Что делает CI

Один job **Lint and Playwright tests** выполняется на `ubuntu-latest` с лимитом 30 минут:

1. Получает код репозитория.
2. Устанавливает Node.js 24 и настраивает кэш npm.
3. Выполняет `npm ci`.
4. Устанавливает Chromium, Firefox, WebKit и системные зависимости.
5. Запускает `npm run lint`.
6. Выполняет `npm test`: unit, API и E2E в трёх браузерах.
7. Загружает `playwright-report/` в artifact `playwright-report-<run_id>` на 14 дней.

После ошибки тестов шаг загрузки отчёта также выполняется, если запуск не отменён. Если тесты не начались, например из-за ошибки установки или линтера, отчёта может не быть.

Результаты доступны в **Pull Request → Checks** и **Actions → Playwright CI → нужный запуск**. Чтобы посмотреть отчёт, скачай artifact, распакуй его и выполни:

```bash
npx playwright show-report /полный/путь/к/распакованному/отчёту
```

Путь должен указывать на папку с `index.html`.

## Уведомления в Telegram

Workflow `.github/workflows/telegram-notify.yml` (**Telegram notification**) запускается после завершения **Playwright CI**. Сообщение отправляется только при результате `success` и содержит репозиторий, ветку, номер и ссылку на запуск. Падения и отмены не отправляются.

Для настройки личных уведомлений:

1. Создай бота через [@BotFather](https://t.me/BotFather), команда `/newbot`, и сохрани токен.
2. Открой своего бота, нажми **Start** и отправь сообщение.
3. Получи ID личного чата из `message.chat.id` ответа метода [getUpdates](https://core.telegram.org/bots/api#getupdates) своего бота.
4. В **Settings → Secrets and variables → Actions → Secrets** создай repository secrets:

   | Secret | Значение |
   | --- | --- |
   | `TELEGRAM_BOT_TOKEN` | Токен бота от BotFather |
   | `TELEGRAM_CHAT_ID` | Числовой ID чата получателя |

5. Добавь файл уведомлений в основную ветку `main`: это необходимо для события `workflow_run`.
6. Запусти **Playwright CI** вручную и после успешного результата проверь Telegram и запуск **Telegram notification**.

Секреты не сохраняются в коде и не переносятся при клонировании: их нужно настроить в своём GitHub-репозитории. Сбой отправки виден в отдельном workflow уведомлений и не меняет результат уже завершившегося Playwright CI. Успешный PR и последующий merge могут дать два сообщения, поскольку это разные прогоны.

## Структура проекта

```text
.github/workflows/
  playwright.yml          # линтер, тесты, HTML-artifact
  telegram-notify.yml     # сообщение после успешного CI
src/pyramid/
  slots.ts                # функции для unit-тестов
  mock-booking-api.ts     # локальный HTTP-мок для API-тестов
tests/
  unit/                   # проверки функций
  api/                    # HTTP-тесты мок-сервера
  e2e/                    # сценарии живого сайта
  helpers/                # пользователи, маршруты, настройки контекстов
  pages/                  # Page Object-классы
eslint.config.mjs         # правила ESLint для тестов
playwright.config.ts      # проекты, браузеры, таймауты и отчёты
package.json              # зависимости и команды npm
package-lock.json         # зафиксированное дерево зависимостей
```

## Работа с изменениями

Создай ветку от актуальной `main`:

```bash
git switch main
git pull --ff-only origin main
git switch -c my-change
```

После изменений выполни линтер и нужные тесты, добавь выбранные файлы в коммит и отправь ветку:

```bash
git add путь/к/изменённому/файлу
git commit -m "Describe the change"
git push -u origin my-change
```

Открой PR внутри `asyakasimova/pomidorQA_CI`: **base — main**, **compare — my-change**. Дождись проверки CI, проверь отчёт и объедини PR. Само наличие workflow не запрещает merge при ошибках: обязательные проверки задаются отдельно правилами защиты ветки на GitHub.
